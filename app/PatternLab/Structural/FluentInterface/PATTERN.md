# Fluent Interface 流式接口

## 1. 一句话定义

通过链式调用让代码表达更接近自然语言。

## 2. 解决什么问题

多个配置步骤分散调用时，可读性差；但链式调用过长也会降低调试性。

## 3. 使用场景

报表查询条件链式构建。

- 业务背景：报表查询条件链式构建。
- 普通写法会让变化点和主流程混在一起。
- 使用该模式后，应把变化点、协作对象或流程步骤拆到独立类中。

## 4. 常见使用地方

- Laravel Query Builder
- Eloquent 查询
- 报表查询构建
- API 参数构建
- 表单配置构建

## 5. 不使用模式可能的问题

- 业务代码容易堆积条件分支或重复流程。
- 新增变化点时修改范围扩大，回归风险升高。
- 单元测试只能覆盖大块流程，难以隔离具体规则。

## 6. 适合使用的情况

- 变化点已经明确，并且预计会继续扩展。
- 同类实现至少有两个，且调用方希望依赖稳定接口。
- 拆分后可以让业务职责、测试目标和扩展边界更清楚。

## 7. 不适合使用的情况

- 当前只有一个简单实现，短期没有扩展需求。
- 引入额外类后可读性反而下降。
- 只是为了套用模式而拆分，没有真实复杂度需要管理。

## 8. Laravel 中的关联点

Laravel Query Builder、Collection 和部分测试 API 都大量使用流式接口。

## 9. 本练习场景

本练习使用“报表查询条件链式构建。”作为业务背景。请只在本目录中完成自己的实现，不要把练习代码散落到已有业务模块。

## 10. 练习目标

- 每个方法返回 $this
- 链式构建查询配置
- 理解可读性和调试成本
- 避免链式调用过长

## 11. 练习内容

**具体功能：报表查询链式 DSL**

你正在实现一个报表查询配置器，让调用方用链式调用表达指标、维度、时间范围、排序和分页。

具体要求：

- 设计每个配置方法都返回当前对象或新的配置对象。
- 链式调用应能表达 `metric()->groupBy()->between()->sortBy()->paginate()`。
- 在 Exercise.php::run() 中构建“收入按城市分组并按金额倒序”的查询配置。
- 补充测试验证链式顺序、最终配置和过长链式调用的可读性边界。

## 12. 建议创建的类

- ReportCriteria.php
- ReportCriteriaBuilder.php

## 13. 测试建议

- 覆盖正常路径和至少一个边界场景。
- 验证调用方只依赖稳定入口，而不是依赖具体实现细节。
- 测试文件先使用 `markTestIncomplete()` 占位，完成练习后再替换为真实断言。

## 14. 面试表达

流式接口的重点不是类数量，而是把“会变化的部分”和“稳定调用方”分开。说明时可以先讲业务场景，再讲普通写法的问题，最后说明该模式如何降低修改范围。

在 Laravel 项目中，应优先利用服务容器、事件、队列、Pipeline、FormRequest 等框架机制。只有当这些机制背后的设计边界需要被明确表达时，再引入单独的模式类。
