# Builder 建造者模式

## 1. 一句话定义

把复杂对象的构建过程拆成多个步骤，使构建过程更清晰。

## 2. 解决什么问题

复杂查询对象参数很多时，构造函数会变长，调用方难以看出每个参数的含义。

## 3. 使用场景

构建复杂报表查询条件。

- 业务背景：构建复杂报表查询条件。
- 普通写法会让变化点和主流程混在一起。
- 使用该模式后，应把变化点、协作对象或流程步骤拆到独立类中。

## 4. 常见使用地方

- 查询条件构建
- 报表配置构建
- API 请求参数构建
- 消息体构建
- 复杂 DTO 构建

## 5. 不使用模式可能的问题

- 业务代码容易堆积条件分支或重复流程。
- 新增变化点时修改范围扩大，回归风险升高。
- 单元测试只能覆盖大块流程，难以隔离具体规则。

## 6. 适合使用的情况

- 变化点已经明确，并且预计会继续扩展。
- 同类实现至少有两个，且调用方希望依赖稳定接口。
- 拆分后可以让业务职责、测试目标和扩展边界更清楚。

## 7. 不适合使用的情况

- 当前只有一个简单实现，短期没有扩展需求。
- 引入额外类后可读性反而下降。
- 只是为了套用模式而拆分，没有真实复杂度需要管理。

## 8. Laravel 中的关联点

Laravel Query Builder 和部分配置对象都体现了分步骤构建复杂对象的思想。

## 9. 本练习场景

本练习使用“构建复杂报表查询条件。”作为业务背景。请只在本目录中完成自己的实现，不要把练习代码散落到已有业务模块。

## 10. 练习目标

- 设计报表查询对象
- 设计 Builder
- 分步骤设置查询条件
- 避免构造函数参数过多

## 11. 练习内容

**具体功能：复杂报表查询条件构建器**

你正在实现一个指标报表查询功能，用户可以选择指标、维度、时间范围、过滤条件、排序和分页参数。

具体要求：

- 设计一个报表查询条件对象，表达 metric、dimension、date range、filters、sort、page。
- 使用 Builder 分步骤设置查询条件，避免构造函数参数过长。
- 在 Exercise.php::run() 中构建“最近 30 天按地区统计收入”的查询条件。
- 补充测试验证必填项、默认分页和链式构建结果。

## 12. 建议创建的类

- ReportQuery.php
- ReportQueryBuilder.php
- ReportFilter.php
- ReportSort.php

## 13. 测试建议

- 覆盖正常路径和至少一个边界场景。
- 验证调用方只依赖稳定入口，而不是依赖具体实现细节。
- 测试文件先使用 `markTestIncomplete()` 占位，完成练习后再替换为真实断言。

## 14. 面试表达

建造者模式的重点不是类数量，而是把“会变化的部分”和“稳定调用方”分开。说明时可以先讲业务场景，再讲普通写法的问题，最后说明该模式如何降低修改范围。

在 Laravel 项目中，应优先利用服务容器、事件、队列、Pipeline、FormRequest 等框架机制。只有当这些机制背后的设计边界需要被明确表达时，再引入单独的模式类。
