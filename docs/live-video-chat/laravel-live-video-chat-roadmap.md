# Laravel 视频分享、直播、聊天项目后续推进路线

> 适用项目：Laravel 13 视频播放 / 直播房间 / 在线聊天学习项目  
> 当前基础：已具备视频上传、FFmpeg 处理、HLS 播放、多码率扩展方向、直播房间、MediaMTX 推流、Reverb 聊天等基础能力。  
> 本文目标：从“学习型 Demo”继续推进到“相对完整的视频分享、直播、聊天网站”，并按 **功能项** 与 **技术点** 区分。

---

## 1. 当前项目定位

当前项目已经覆盖了视频、直播、聊天的技术主干：

```text
视频上传
-> 队列异步处理
-> FFmpeg / ffprobe 解析和转码
-> HLS 播放
-> 直播房间
-> MediaMTX 真推流
-> Reverb 实时聊天
```

它已经不只是普通 Laravel CRUD 项目，而是一个具备多媒体处理、实时通信、队列异步任务、Docker 中间件和直播架构雏形的综合学习项目。

后续如果继续完善，可以从以下方向推进：

```text
视频分享网站能力
直播网站能力
聊天室 / 私信 / 通知能力
内容审核与安全
工程化和生产化
后台管理系统
```

## 2. 分类原则

后续功能可以分为两类：

### 2.1 偏功能型需求

这类主要是产品功能和页面交互，技术复杂度相对低，重点是业务流程、数据库设计、页面展示。

例如：

```text
用户头像
用户昵称
用户主页
视频分类
视频标签
视频收藏
视频简介
直播间封面
视频发布状态
```

### 2.2 偏技术型需求

这类不仅是功能，还涉及架构、性能、实时性、安全性或中间件设计。

例如：

```text
直播间实时在线人数
视频转码队列
多码率 HLS
推流状态检测
WebSocket 聊天
HLS 防盗链
私信未读数
Redis 限流
对象存储 MinIO
队列失败重试
```

后续拆 Codex 任务时，应优先区分：

```text
这个需求只是新增页面和字段？
还是涉及 WebSocket、Redis、Queue、FFmpeg、Storage、安全校验、调度任务？
```

## 3.2 视频发布流程

### 功能项

| 功能 | 说明 | 优先级 |
|---|---|---|
| 上传视频 | 已有基础，可继续完善 | P0 |
| 转码状态展示 | 展示处理中、失败、完成 | P0 |
| 编辑标题 | 上传后修改标题 | P1 |
| 编辑简介 | 修改视频描述 | P1 |
| 选择封面 | 使用自动封面或手动上传封面 | P2 |
| 分类 | 选择视频分类 | P1 |
| 标签 | 添加多个标签 | P1 |
| 草稿 | 视频未发布前保存为草稿 | P2 |
| 发布 | 转码完成后发布 | P1 |
| 下架 | 作者或管理员下架视频 | P2 |
| 审核 | 管理员审核后上架 | P2 |

### 技术点

| 技术点 | 说明 |
|---|---|
| 状态机设计 | uploaded / processing / ready / draft / published / rejected / hidden |
| FormRequest | 视频标题、简介、分类、标签校验 |
| Queue Job | 视频处理、封面生成、HLS 转码 |
| Eloquent 关联 | 视频和用户、分类、标签关联 |
| 事务处理 | 发布时同时处理视频状态和标签关系 |
| 后台审核 | 管理员审核需要权限系统 |

### 推荐视频状态设计

```text
uploaded       已上传
processing     处理中
ready          已处理完成
draft          草稿
published      已发布
rejected       审核失败
hidden         隐藏
deleted        删除
failed         处理失败
```

### 说明

现在项目中的 `pending / processing / ready / failed` 更偏技术处理状态。后续可以拆成：

```text
processing_status：处理状态
publish_status：发布状态
```

例如：

```text
processing_status = ready
publish_status = draft
```

表示视频已转码完成，但还没有发布。

### 功能项

| 功能 | 说明 | 优先级 |
|---|---|---|
| 创建直播间 | 主播创建自己的直播间 | P0 |

### 技术点

| 技术点 | 说明 |
|---|---|

### 开播链路

```text

-> 系统生成 stream_key
-> 系统生成 OBS Server 和 Stream Key
-> 主播复制到 OBS
-> OBS 开始推流
-> MediaMTX 输出 HLS
-> Laravel 房间页播放 playback_url
```

## 4.2 直播间实时在线人数

这是一个典型的“功能 + 技术”混合项。

### 功能项

| 功能 | 说明 | 优先级 |
|---|---|---|
| 显示当前在线人数 | 房间页显示当前观众数 | P1 |
| 显示用户进入提示 | 某用户进入直播间 | P2 |
| 显示用户离开提示 | 某用户离开直播间 | P2 |
| 在线用户列表 | 展示当前在线用户 | P3 |
| 历史最高在线 | 记录 peak viewer count | P2 |
| 直播间热度 | 根据在线、点赞、聊天等计算 | P3 |

### 技术点

| 技术点 | 说明 |
|---|---|
| Reverb Presence Channel | 实时感知频道成员 |
| Laravel Echo | 前端订阅 presence channel |
| Redis Set | 记录房间当前在线用户集合 |
| TTL / 心跳 | 防止用户异常断开后一直在线 |
| 并发一致性 | 多窗口、刷新、断线重连处理 |
| peak_viewer_count | 在线人数超过历史峰值时更新 |
| Scheduler | 定期清理过期在线记录 |

### 推荐实现层次

#### 第一版：只用 Presence Channel

```text
用户进入房间
-> Echo join presence-live-room.{id}
-> 前端 here / joining / leaving 更新人数
```

优点：实现快。  
缺点：数据主要在 WebSocket 层，后端持久化能力弱。

#### 第二版：Presence Channel + Redis

```text
用户进入房间
-> Reverb presence 触发前端变化
-> 后端 API / 心跳写 Redis Set
-> Redis 统计在线人数
-> 定期同步 peak_viewer_count 到 MySQL
```

优点：更接近真实系统。  
缺点：要处理过期、断线、重复窗口。

### 推荐学习实现

```text
Phase A：用 Reverb presence 实现前端实时人数
Phase B：用 Redis 记录 room:{id}:online_users
Phase C：记录 peak_viewer_count
Phase D：增加心跳和过期清理
```

## 4.3 推流状态检测

### 功能项

| 功能 | 说明 | 优先级 |
|---|---|---|
| 自动判断是否开播 | OBS 推流后房间自动 live | P1 |
| 自动判断断流 | OBS 停止后房间自动 ended / offline | P1 |
| 页面显示推流状态 | 推流中、未推流、断流 | P1 |
| 管理员查看异常直播 | 查看断流或异常房间 | P3 |

### 技术点

| 技术点 | 说明 |
|---|---|
| HTTP 探测 m3u8 | 请求 playback_url 判断是否可访问 |
| Laravel Scheduler | 定时检测直播状态 |
| Media Server API | 后续可用 MediaMTX / SRS API 或回调 |
| 状态防抖 | 避免一次 404 就判定下播 |
| 时间窗口 | 连续多次失败后才更新状态 |
| 队列任务 | 大量直播间检测可异步执行 |

### 简化方案

```text
每 30 秒检查 live_rooms 中 scheduled / live 的房间
请求 playback_url
如果连续 2~3 次成功：标记 live
如果连续 3~5 次失败：标记 ended 或 offline
```

### 注意

HLS 直播会有延迟，OBS 刚开始推流时 `m3u8` 可能不会立刻出现。状态检测需要容忍短暂 404。

# 11. 项目最终可讲解的完整业务闭环

如果后续按推荐路线推进，这个项目可以形成完整闭环：

```text
用户注册登录
-> 上传视频
-> 系统异步转码
-> 生成多码率 HLS
-> 用户编辑标题、简介、分类、标签
-> 发布视频
-> 其他用户观看、评论、点赞、收藏
-> 主播创建直播间
-> 系统生成 stream_key 和 OBS 推流地址
-> 主播使用 OBS 开播
-> 观众进入直播间观看
-> Reverb 实时聊天
-> Redis / Presence 统计在线人数
-> 直播结束后生成回放
-> 回放进入视频库
-> 管理员审核、下架、禁言、处理举报
```

这条链路适合作为简历项目或面试项目讲解。
