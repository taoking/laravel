# 【视频业务成本模型】技术方案设计

> 来源：根据 `docs/live-video-chat/11-senior-backend-interview-system-design.md` 的 `0.3 资深后端面试视角下仍需补充的方向`，并参考 `docs/live-video-chat/prompt.md` 的输出规范整理。

## 1. 模块定位

视频业务成本模型属于 **业务 + 技术混合模块**。

视频业务最贵的是带宽、存储和转码；资深后端需要能把技术选择和成本影响讲清楚。

它涉及的核心组件是：cost_reports、storage_usage、cdn_bandwidth、transcode_cost、metrics aggregation、Grafana。

## 2. 解决的问题

- 用户层面：平台能在保证体验的前提下控制成本，避免热门内容和转码策略导致费用失控。
- 系统层面：建立存储、转码、CDN、回源、直播、日志和数据分析的成本指标和估算模型。
- 如果不做：技术方案只讲性能不讲成本，会在真实视频业务中不可持续。
- 在视频 / 直播 / 聊天平台中的位置：横跨转码、存储、CDN、直播和数据平台，是生产架构取舍的核心依据。

## 3. 常见方案对比

| 方案 | 核心思路 | 需要组件 | 优点 | 缺点 | 适合阶段 | 是否推荐 |
| --- | --- | --- | --- | --- | --- | --- |
| 人工估算表 | 用文档和表格估算成本 | Excel/Markdown | 简单 | 不实时 | 学习版 | 推荐起步 |
| 指标表 + 日报 | 每日聚合存储、带宽、转码耗时 | MySQL、Queue | 可持续跟踪 | 需要采集数据 | 项目展示版 | 推荐 |
| 云账单接入 | 拉取云厂商 CDN/OSS/转码账单 | 云 API、Job | 真实准确 | 供应商适配 | 生产环境 | 推荐生产 |
| 成本优化平台 | 按业务、创作者、内容类型分摊成本 | 数据仓库、报表 | 管理精细 | 复杂 | 大型平台 | 设计理解 |

## 4. 推荐学习方案

当前学习项目推荐方案：

```text
方案名称：容量估算文档 + 日级成本指标表 + 成本面板
核心组件：storage_usage_daily、cdn_usage_daily、transcode_cost_logs、CostReportService
Laravel 职责：采集业务维度、聚合成本指标、给后台展示趋势和异常
中间件职责：对象存储/CDN/云服务提供用量数据，队列定时同步
数据流：每日采集存储/带宽/转码数据 -> 汇总成本 -> 按视频/创作者/模块归因 -> 生成报表
适合原因：能把视频平台最现实的问题讲清楚
不足：本地环境没有真实云账单，只能模拟估算
后续升级：云账单 API、成本告警、按业务线分摊
```

## 5. 生产环境方案、容量和架构设计

### 5.1 生产环境常见方案

| 方案 | 典型架构 | 适合规模 | 优点 | 缺点 | 成本 | 维护难度 | 是否推荐 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 小型业务方案 | Laravel + MySQL + Redis，成本分析服务 以规则和配置为主 | 学习项目到小型产品 | 实现成本低，易排查 | 能力边界有限 | 低 | 低 | 推荐学习 |
| 中型业务方案 | cost_reports、storage_usage、cdn_bandwidth、transcode_cost、metrics aggregation、Grafana，增加异步任务、缓存、后台和指标 | 稳定增长业务 | 可扩展，可运营 | 需要监控和运维 | 中 | 中 | 推荐演进 |
| 大型业务方案 | 成本分析服务 平台化，接入事件流、OLAP、调度、自动化治理 | 高并发平台 | 能力完整，抗风险强 | 复杂度和成本高 | 高 | 高 | 只做设计理解 |
| 云服务方案 | 使用云厂商托管能力或第三方 SaaS | 快速上线或团队较小 | 省运维，稳定 | 厂商绑定和费用不可忽视 | 中到高 | 低到中 | 生产可选 |
| 自建方案 | 自建数据、调度、风控、媒体或分析平台 | 有基础设施团队 | 可控性强 | 建设周期长 | 高 | 高 | 大型团队再考虑 |

### 5.2 生产环境容量估算

需要提前估算：

- 日上传 GB、日播放 TB、转码输出倍数、直播带宽峰值、日志保留量、CDN 单价

估算方式：

```text
先从业务峰值倒推技术容量：用户量、请求量、事件量、文件量、带宽、队列任务和缓存规模。
再按高峰系数、保留周期、失败重试比例和降级策略估算真实资源。
如果容量估算无法解释成本和瓶颈，这个设计就还停留在 Demo 层面。
```

### 5.3 关键设计问题

- Laravel 负责业务控制、权限、元数据、状态流转和后台管理。
- 高频、耗时、可失败的动作要进入 Redis、Queue、媒体服务、数据平台或 CDN。
- 生产设计必须说明一致性边界：哪些强一致，哪些最终一致，哪些允许降级。
- 资深后端面试中要主动说明容量、成本、稳定性、安全和演进路线。

### 5.4 典型容量瓶颈和解决方式

| 瓶颈 | 表现 | 原因 | 解决方式 |
| --- | --- | --- | --- |
| CDN 流量成本过高 | 延迟升高、错误增加、成本上升或数据不准 | 访问量、数据量或组件能力超过当前设计 | 加缓存、异步化、分层拆分、容量规划、监控告警和降级策略 |
| 多码率转码输出膨胀 | 延迟升高、错误增加、成本上升或数据不准 | 访问量、数据量或组件能力超过当前设计 | 加缓存、异步化、分层拆分、容量规划、监控告警和降级策略 |
| 冷数据长期占用存储 | 延迟升高、错误增加、成本上升或数据不准 | 访问量、数据量或组件能力超过当前设计 | 加缓存、异步化、分层拆分、容量规划、监控告警和降级策略 |
| 日志和事件数据成本失控 | 延迟升高、错误增加、成本上升或数据不准 | 访问量、数据量或组件能力超过当前设计 | 加缓存、异步化、分层拆分、容量规划、监控告警和降级策略 |

### 5.5 学习版到生产版的演进路线

- 本地学习版：用 Laravel、MySQL、Redis 和少量配置跑通核心流程。
- 项目展示版：增加状态表、后台入口、Redis 缓存/队列、指标和失败重试。
- 小型生产版：接入对象存储、CDN、Nginx、Supervisor、告警和备份。
- 中大型生产版：按能力拆分专门服务，接入 Kafka、OLAP、调度、风控、HA 和成本治理。
- 云服务方案：优先使用云托管能力降低运维难度，再保留业务抽象避免强绑定。

### 5.6 生产环境面试讲解

如果从 Demo 升级到生产，我会先定义容量指标和故障边界，再把同步链路压到最短；Laravel 只做业务判断和元数据更新，吞吐型任务交给中间件或专门服务。这个模块最容易被追问的是：CDN 流量成本过高、多码率转码输出膨胀、冷数据长期占用存储，所以需要提前准备降级、监控和成本口径。

## 7. 核心流程

### 正常流程

1. 用户或客户端发起请求。
2. Laravel 完成认证、授权、参数校验和业务策略判断。
3. Redis 处理缓存、限流、锁、短期状态或热点数据。
4. MySQL 记录核心业务状态、配置、审计和聚合结果。
5. Queue 处理异步计算、同步、聚合、导出或通知。
6. 成本分析服务 执行该模块的核心平台能力。
7. 前端或后台读取结果，并通过日志、指标或通知观察处理状态。

### 异常流程

- 中间件不可用：走降级策略，使用缓存快照或返回可理解的错误。
- 队列积压：限制入口流量，降低非核心任务优先级，扩容 worker。
- 数据不一致：通过幂等键、状态机、补偿 Job 和定时校准修复。
- 权限不足：返回 403，关键动作写审计日志。
- 外部服务失败：设置 timeout、重试、熔断和人工处理入口。

## 8. Laravel 实现拆分

### 8.1 数据库表

- storage_usage_daily：date、asset_type、bytes、cost
- cdn_usage_daily：date、provider、traffic_bytes、bandwidth_peak、cost
- transcode_cost_logs：video_id、duration_seconds、cpu_seconds、output_bytes
- cost_alerts：metric、threshold、status

### 8.2 Model

- CostReport hasMany CostItems
- Video hasMany TranscodeCostLog

### 8.3 Controller

- AdminCostDashboardController：成本概览
- AdminCostAlertController：成本告警配置

Controller 只负责接收请求、调用授权、组织响应；核心策略放在 Service，耗时逻辑放在 Job。

### 8.4 Service / Support / Action

- CostEstimationService：估算单视频成本
- CloudBillingSyncService：同步云账单
- CostAttributionService：按视频/创作者归因

### 8.5 Job

- AggregateDailyCostJob
- SyncCloudBillingJob
- DetectCostAnomalyJob

Job 要设置 `tries`、`timeout`、`backoff`，失败时写入状态和错误摘要，便于后台重试或人工处理。

### 8.6 Event / Listener

- CostThresholdExceeded、DailyCostReportGenerated

### 8.7 WebSocket / Broadcasting

- private-admin.costs 推送成本异常

### 8.8 Policy / Middleware

- 只有管理员可查看全站成本；创作者只看自己的粗略数据

## 10. 数据和状态设计

核心状态：

- cost_report.status：collecting -> calculated -> reviewed
- cost_alert.status：open -> acknowledged -> resolved

状态设计说明：

- 状态迁移必须有明确触发者：用户、管理员、队列任务、定时任务或外部回调。
- 状态失败必须保留原因，并提供重试、跳过、回滚或人工处理方式。
- 前台页面展示业务状态，后台保留技术状态和错误详情。

## 11. Redis / Queue / WebSocket 使用方式

### 11.1 Redis

- 成本面板缓存
- 异常检测锁
- 热点视频成本短期计数

### 11.2 Queue

- 成本聚合和云账单同步异步
- 异常告警可以异步发送

### 11.3 WebSocket / Reverb

- 后台成本异常可实时提示

## 12. 安全风险

- 成本归因不准：明确估算口径
- 云账单延迟：区分实时估算和最终账单
- 过度优化影响体验：成本和 QoE 一起看
- 数据泄露：成本后台权限控制

## 13. 性能和扩展

- 学习版可以先用单机 Laravel + MySQL + Redis 验证流程。
- 当读多写少时，优先做缓存和 CDN。
- 当写入和事件量增加时，优先拆队列、批量写入和数据管道。
- 当单点不可接受时，增加健康检查、主从、多节点和降级开关。
- 当成本开始明显增长时，把 成本分析服务 的核心指标纳入成本报表。

## 14. 监控和排查

重点指标：

- 每日存储增长
- CDN 流量和峰值带宽
- 转码 CPU 成本
- 单播放成本
- 单视频生命周期成本
- 回源成本

本地排查方式：

- `storage/logs/laravel.log`
- `php artisan queue:failed`
- `docker compose logs`
- Redis CLI 查看关键 key
- MySQL 查询状态表、日志表和慢查询
- 浏览器 Network / Console
- 后台管理页查看任务状态和指标快照

## 15. 分阶段实施路线

- Phase 1：文档化容量和成本估算公式
- Phase 2：日级存储/转码/CDN 成本表和后台面板
- Phase 3：云账单接入、成本归因、异常告警和优化策略

验收标准：

- Phase 1：本地能手动跑通主流程，并能说清楚核心原理。
- Phase 2：有状态表、后台入口、异步任务、指标和异常处理。
- Phase 3：能说明生产环境扩展、降级、监控、成本和风险控制。

## 16. 面试讲解角度

### 16.1 这个功能为什么要这样设计？

因为 技术方案只讲性能不讲成本，会在真实视频业务中不可持续。，所以需要平台级设计，而不是只在 Controller 中补几行逻辑。

### 16.2 Laravel 在里面负责什么？

Laravel 负责业务策略、权限、状态、元数据、后台管理、任务派发和结果查询。

### 16.3 中间件负责什么？

中间件负责高吞吐、低延迟、异步化、数据分析、媒体处理、缓存分发或基础设施能力。

### 16.4 为什么不能全部用 Laravel 直接做？

Laravel 不适合承载媒体流、大规模事件、高频实时计算、复杂调度和海量分析。它应该作为业务控制层，而不是所有基础设施的替代品。

### 16.5 如果数据量 / 流量变大，怎么扩展？

先缓存和异步化，再拆专门服务；先做单机可观察，再做多节点和容灾；先用规则可解释方案，再引入复杂平台能力。

### 16.6 失败场景怎么处理？

通过状态机、幂等键、重试、死信、补偿任务、降级开关和后台人工处理入口处理失败。

### 16.7 安全风险怎么处理？

围绕权限、输入校验、限流、签名、审计、隐私和误操作防护设计安全边界。

### 16.8 这个方案还有哪些不足？

学习版主要用于理解和面试讲解，不等价于真实大厂平台。真正生产还需要组织流程、SLA、成本预算、专门团队和长期数据积累。

## 17. 总结

视频成本模型的核心是把每个技术决策换算成存储、带宽、转码和运维成本，支撑架构取舍。

## 一句话总结

视频业务成本模型的核心是：让 Laravel 站在业务控制层，平台组件承担高吞吐和基础设施能力，并用容量、成本、稳定性和安全边界证明设计可以从 Demo 演进到生产。
