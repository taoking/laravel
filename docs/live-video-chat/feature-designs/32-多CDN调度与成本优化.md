# 【多 CDN 调度与成本优化】技术方案设计

> 来源：根据 `docs/live-video-chat/11-senior-backend-interview-system-design.md` 的 `0.3 资深后端面试视角下仍需补充的方向`，并参考 `docs/live-video-chat/prompt.md` 的输出规范整理。

## 1. 模块定位

多 CDN 调度与成本优化属于 **技术功能模块**。

大视频平台通常不会只依赖一个 CDN，需要按地域、质量、成本、命中率和故障情况进行调度。

它涉及的核心组件是：CDN 域名、调度策略、地域识别、QoE 上报、成本报表、回源配置、签名 URL。

## 2. 解决的问题

- 用户层面：不同地区用户能获得更稳定、更快的视频播放体验。
- 系统层面：在多个 CDN 供应商之间选择合适播放域名，并监控质量和成本。
- 如果不做：单 CDN 故障会影响全站播放，成本也缺少优化空间。
- 在视频 / 直播 / 聊天平台中的位置：位于对象存储/源站和用户播放器之间，是大流量视频分发成本控制的重要层。

## 3. 常见方案对比

| 方案 | 核心思路 | 需要组件 | 优点 | 缺点 | 适合阶段 | 是否推荐 |
| --- | --- | --- | --- | --- | --- | --- |
| 单 CDN | 所有视频使用一个 CDN 域名 | CDN | 简单稳定 | 单供应商风险 | 小型生产 | 推荐起步 |
| 按地域静态分配 | 不同地区返回不同 CDN 域名 | IP 地域库、配置表 | 易理解 | 不够动态 | 中型业务 | 推荐演进 |
| 质量 + 成本动态调度 | 结合失败率、延迟、带宽价格选择 CDN | QoE、成本模型、调度服务 | 体验和成本平衡 | 实现复杂 | 大型业务 | 生产设计 |
| 云厂商智能调度 | 使用云解析或融合 CDN | 云 DNS/融合 CDN | 省研发 | 供应商依赖 | 生产可选 | 可选 |

## 4. 推荐学习方案

当前学习项目推荐方案：

```text
方案名称：单 CDN 抽象 + 地域配置预留 + QoE 上报
核心组件：cdn_providers、cdn_routes、CdnUrlService、playback_error_events
Laravel 职责：生成 CDN URL、按配置选择域名、记录播放质量、提供切换开关
中间件职责：CDN 分发 HLS/封面，DNS 或调度层完成就近访问
数据流：播放页请求 -> Laravel 判断地区/策略 -> 返回 CDN A/B URL -> 播放器上报错误和延迟 -> 后台分析调整
适合原因：学习项目不用接多家 CDN，也能设计可替换抽象
不足：真实调度需要大量质量和成本数据
后续升级：多 CDN、融合调度、成本优化、故障自动切换
```

## 5. 生产环境方案、容量和架构设计

### 5.1 生产环境常见方案

| 方案 | 典型架构 | 适合规模 | 优点 | 缺点 | 成本 | 维护难度 | 是否推荐 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 小型业务方案 | Laravel + MySQL + Redis，CDN 调度服务 以规则和配置为主 | 学习项目到小型产品 | 实现成本低，易排查 | 能力边界有限 | 低 | 低 | 推荐学习 |
| 中型业务方案 | CDN 域名、调度策略、地域识别、QoE 上报、成本报表、回源配置、签名 URL，增加异步任务、缓存、后台和指标 | 稳定增长业务 | 可扩展，可运营 | 需要监控和运维 | 中 | 中 | 推荐演进 |
| 大型业务方案 | CDN 调度服务 平台化，接入事件流、OLAP、调度、自动化治理 | 高并发平台 | 能力完整，抗风险强 | 复杂度和成本高 | 高 | 高 | 只做设计理解 |
| 云服务方案 | 使用云厂商托管能力或第三方 SaaS | 快速上线或团队较小 | 省运维，稳定 | 厂商绑定和费用不可忽视 | 中到高 | 低到中 | 生产可选 |
| 自建方案 | 自建数据、调度、风控、媒体或分析平台 | 有基础设施团队 | 可控性强 | 建设周期长 | 高 | 高 | 大型团队再考虑 |

### 5.2 生产环境容量估算

需要提前估算：

- 每日播放流量、地域分布、峰值带宽、回源比例、签名 URL QPS、CDN 供应商数量

估算方式：

```text
先从业务峰值倒推技术容量：用户量、请求量、事件量、文件量、带宽、队列任务和缓存规模。
再按高峰系数、保留周期、失败重试比例和降级策略估算真实资源。
如果容量估算无法解释成本和瓶颈，这个设计就还停留在 Demo 层面。
```

### 5.3 关键设计问题

- Laravel 负责业务控制、权限、元数据、状态流转和后台管理。
- 高频、耗时、可失败的动作要进入 Redis、Queue、媒体服务、数据平台或 CDN。
- 生产设计必须说明一致性边界：哪些强一致，哪些最终一致，哪些允许降级。
- 资深后端面试中要主动说明容量、成本、稳定性、安全和演进路线。

### 5.4 典型容量瓶颈和解决方式

| 瓶颈 | 表现 | 原因 | 解决方式 |
| --- | --- | --- | --- |
| 单 CDN 故障 | 延迟升高、错误增加、成本上升或数据不准 | 访问量、数据量或组件能力超过当前设计 | 加缓存、异步化、分层拆分、容量规划、监控告警和降级策略 |
| 回源带宽过高 | 延迟升高、错误增加、成本上升或数据不准 | 访问量、数据量或组件能力超过当前设计 | 加缓存、异步化、分层拆分、容量规划、监控告警和降级策略 |
| 签名 URL 生成压力 | 延迟升高、错误增加、成本上升或数据不准 | 访问量、数据量或组件能力超过当前设计 | 加缓存、异步化、分层拆分、容量规划、监控告警和降级策略 |
| 质量数据不足导致调度不准 | 延迟升高、错误增加、成本上升或数据不准 | 访问量、数据量或组件能力超过当前设计 | 加缓存、异步化、分层拆分、容量规划、监控告警和降级策略 |

### 5.5 学习版到生产版的演进路线

- 本地学习版：用 Laravel、MySQL、Redis 和少量配置跑通核心流程。
- 项目展示版：增加状态表、后台入口、Redis 缓存/队列、指标和失败重试。
- 小型生产版：接入对象存储、CDN、Nginx、Supervisor、告警和备份。
- 中大型生产版：按能力拆分专门服务，接入 Kafka、OLAP、调度、风控、HA 和成本治理。
- 云服务方案：优先使用云托管能力降低运维难度，再保留业务抽象避免强绑定。

### 5.6 生产环境面试讲解

如果从 Demo 升级到生产，我会先定义容量指标和故障边界，再把同步链路压到最短；Laravel 只做业务判断和元数据更新，吞吐型任务交给中间件或专门服务。这个模块最容易被追问的是：单 CDN 故障、回源带宽过高、签名 URL 生成压力，所以需要提前准备降级、监控和成本口径。

## 7. 核心流程

### 正常流程

1. 用户或客户端发起请求。
2. Laravel 完成认证、授权、参数校验和业务策略判断。
3. Redis 处理缓存、限流、锁、短期状态或热点数据。
4. MySQL 记录核心业务状态、配置、审计和聚合结果。
5. Queue 处理异步计算、同步、聚合、导出或通知。
6. CDN 调度服务 执行该模块的核心平台能力。
7. 前端或后台读取结果，并通过日志、指标或通知观察处理状态。

### 异常流程

- 中间件不可用：走降级策略，使用缓存快照或返回可理解的错误。
- 队列积压：限制入口流量，降低非核心任务优先级，扩容 worker。
- 数据不一致：通过幂等键、状态机、补偿 Job 和定时校准修复。
- 权限不足：返回 403，关键动作写审计日志。
- 外部服务失败：设置 timeout、重试、熔断和人工处理入口。

## 8. Laravel 实现拆分

### 8.1 数据库表

- cdn_providers：name、domain、region、status、cost_per_gb
- cdn_routes：region、provider_id、weight、enabled
- cdn_quality_metrics：provider_id、region、error_rate、latency_ms、timestamp

### 8.2 Model

- CdnProvider hasMany Routes / Metrics
- CdnRoute belongsTo Provider

### 8.3 Controller

- PlaybackUrlController：返回调度后的播放 URL
- AdminCdnController：配置供应商和路由
- PlaybackQualityController：接收 QoE 上报

Controller 只负责接收请求、调用授权、组织响应；核心策略放在 Service，耗时逻辑放在 Job。

### 8.4 Service / Support / Action

- CdnUrlService：签名和域名拼接
- CdnScheduler：按地域、权重、健康选择 CDN
- CdnCostAnalyzer：计算成本和回源比例

### 8.5 Job

- AggregateCdnQualityJob
- SyncCdnCostReportJob
- SwitchCdnRouteOnFailureJob

Job 要设置 `tries`、`timeout`、`backoff`，失败时写入状态和错误摘要，便于后台重试或人工处理。

### 8.6 Event / Listener

- CdnProviderDegraded、CdnRouteChanged、PlaybackCdnErrorReported

### 8.7 WebSocket / Broadcasting

- private-admin.cdn 推送 CDN 异常和切换事件

### 8.8 Policy / Middleware

- 只有管理员可修改 CDN 策略；播放 URL 生成要遵守视频访问权限

## 9. Docker 组件选择

| 组件 | 镜像示例 | 用途 | 本地学习是否需要 |
| --- | --- | --- | --- |
| MySQL | mysql:8.0 | 业务元数据、状态、审计日志 | 需要 |
| Redis | redis:7-alpine | 缓存、限流、队列、计数、锁 | 多数模块需要 |
| Nginx | nginx | 本地模拟多个 CDN 域名 | 后续扩展 |
| Grafana | grafana/grafana | CDN 质量和成本面板 | 后续扩展 |

## 10. 数据和状态设计

核心状态：

- cdn_provider.status：healthy -> degraded -> disabled
- cdn_route.status：active -> draining -> inactive

状态设计说明：

- 状态迁移必须有明确触发者：用户、管理员、队列任务、定时任务或外部回调。
- 状态失败必须保留原因，并提供重试、跳过、回滚或人工处理方式。
- 前台页面展示业务状态，后台保留技术状态和错误详情。

## 11. Redis / Queue / WebSocket 使用方式

### 11.1 Redis

- CDN 调度结果短缓存
- 供应商健康状态缓存
- 播放错误计数器

### 11.2 Queue

- 质量聚合、成本报表、自动切换异步执行
- 播放 URL 生成不能等待外部 CDN API

### 11.3 WebSocket / Reverb

- 后台告警可实时推送，播放器切 CDN 通常靠重试逻辑

## 12. 安全风险

- 签名 URL 不一致：统一 CdnUrlService
- 缓存污染：版本化路径和正确 Cache-Control
- 误切 CDN：阈值和人工确认
- 成本失控：带宽和回源日报

## 13. 性能和扩展

- 学习版可以先用单机 Laravel + MySQL + Redis 验证流程。
- 当读多写少时，优先做缓存和 CDN。
- 当写入和事件量增加时，优先拆队列、批量写入和数据管道。
- 当单点不可接受时，增加健康检查、主从、多节点和降级开关。
- 当成本开始明显增长时，把 CDN 调度服务 的核心指标纳入成本报表。

## 14. 监控和排查

重点指标：

- CDN 命中率
- 回源带宽
- 播放错误率
- P95 首片延迟
- 每 GB 成本
- 供应商可用性

本地排查方式：

- `storage/logs/laravel.log`
- `php artisan queue:failed`
- `docker compose logs`
- Redis CLI 查看关键 key
- MySQL 查询状态表、日志表和慢查询
- 浏览器 Network / Console
- 后台管理页查看任务状态和指标快照

## 15. 分阶段实施路线

- Phase 1：抽象 CdnUrlService，支持单 CDN 域名
- Phase 2：供应商表、地域路由、QoE 上报和手动切换
- Phase 3：动态调度、成本报表、故障自动降级和融合 CDN

验收标准：

- Phase 1：本地能手动跑通主流程，并能说清楚核心原理。
- Phase 2：有状态表、后台入口、异步任务、指标和异常处理。
- Phase 3：能说明生产环境扩展、降级、监控、成本和风险控制。

## 16. 面试讲解角度

### 16.1 这个功能为什么要这样设计？

因为 单 CDN 故障会影响全站播放，成本也缺少优化空间。，所以需要平台级设计，而不是只在 Controller 中补几行逻辑。

### 16.2 Laravel 在里面负责什么？

Laravel 负责业务策略、权限、状态、元数据、后台管理、任务派发和结果查询。

### 16.3 中间件负责什么？

中间件负责高吞吐、低延迟、异步化、数据分析、媒体处理、缓存分发或基础设施能力。

### 16.4 为什么不能全部用 Laravel 直接做？

Laravel 不适合承载媒体流、大规模事件、高频实时计算、复杂调度和海量分析。它应该作为业务控制层，而不是所有基础设施的替代品。

### 16.5 如果数据量 / 流量变大，怎么扩展？

先缓存和异步化，再拆专门服务；先做单机可观察，再做多节点和容灾；先用规则可解释方案，再引入复杂平台能力。

### 16.6 失败场景怎么处理？

通过状态机、幂等键、重试、死信、补偿任务、降级开关和后台人工处理入口处理失败。

### 16.7 安全风险怎么处理？

围绕权限、输入校验、限流、签名、审计、隐私和误操作防护设计安全边界。

### 16.8 这个方案还有哪些不足？

学习版主要用于理解和面试讲解，不等价于真实大厂平台。真正生产还需要组织流程、SLA、成本预算、专门团队和长期数据积累。

## 17. 总结

多 CDN 调度的核心是在播放质量、成本和可用性之间做选择，并把 CDN 域名生成从业务代码中抽象出来。

## 一句话总结

多 CDN 调度与成本优化的核心是：让 Laravel 站在业务控制层，平台组件承担高吞吐和基础设施能力，并用容量、成本、稳定性和安全边界证明设计可以从 Demo 演进到生产。
