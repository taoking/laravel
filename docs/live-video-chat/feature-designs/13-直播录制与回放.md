# 【直播录制与回放】技术方案设计

> 来源：根据 `docs/live-video-chat/10-mainstream-roadmap.md`、`docs/live-video-chat/laravel-live-video-chat-roadmap.md` 和 `docs/live-video-chat/prompt.md` 整理。

## 1. 模块定位

直播录制与回放属于 **业务 + 技术混合模块**。

直播回放需要媒体服务器录制、文件接入、队列转码、视频记录、存储生命周期和发布权限。

它涉及的核心组件是：MediaMTX/SRS recording、live_recordings、Queue、FFmpeg、videos、Storage、HLS。

## 2. 解决的问题

- 用户层面：直播结束后主播和观众可以查看往期直播回放。
- 系统层面：把直播流产生的录制文件转入点播处理流水线，生成可播放 HLS。
- 不做的问题：直播结束内容就丢失，无法形成内容沉淀和创作者资产。
- 所在位置：它连接直播系统和视频点播系统，是主流平台常见闭环。

## 3. 常见方案对比

| 方案 | 核心思路 | 需要组件 | 优点 | 缺点 | 适合阶段 | 是否推荐 |
| --- | --- | --- | --- | --- | --- | --- |
| 不录制 | 直播结束即丢弃内容 | Media server | 最简单 | 没有回放 | 早期 Demo | 可接受 |
| 媒体服务器本地录制 | MediaMTX/SRS 保存文件，Laravel 扫描接入 | Media server、Storage | 本地可学 | 文件命名和回调要处理 | 学习项目 | 推荐 |
| 录制后进入点播转码 | 创建 video 记录并复用 HLS 处理 | Queue、FFmpeg | 复用现有能力 | 耗时和存储成本高 | 项目展示版 | 推荐升级 |
| 云直播录制回放 | 云服务直接生成回放和回调 | 云直播/云点播 | 稳定省心 | 成本高 | 生产环境 | 可选 |

## 4. 推荐学习方案

当前学习项目推荐方案：

```text
方案名称：MediaMTX 录制文件 + Laravel 接入 + 复用视频转码流水线
核心组件：MediaMTX recording、live_recordings、Queue、FFmpeg、videos
Laravel 职责：记录录制文件、创建回放视频、派发转码、控制发布状态
中间件职责：媒体服务器负责录制，FFmpeg worker 负责回放转 HLS
数据流：直播结束 -> 录制文件完成 -> Laravel callback/扫描 -> 创建 recording/video -> 转码 -> 发布回放
适合原因：能把直播和点播主线串成完整闭环
不足：录制文件大，失败恢复和清理要做
后续升级：云录制、分段录制、精彩片段剪辑
```

## 5. 生产环境方案、容量和架构设计

### 5.1 生产环境常见方案

| 方案 | 典型架构 | 适合规模 | 优点 | 缺点 | 成本 | 维护难度 | 是否推荐 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 小型业务方案 | Laravel + MySQL + Redis，直播回放流水线 单机运行 | 学习项目到小型站点 | 实现成本低，便于排查 | 容量和高可用有限 | 低 | 低 | 学习期推荐 |
| 中型业务方案 | MediaMTX/SRS recording、live_recordings、Queue、FFmpeg、videos、Storage、HLS，队列和缓存拆分，关键任务异步 | 有稳定用户和内容增长 | 吞吐更好，边界清晰 | 需要监控和运维 | 中 | 中 | 推荐演进 |
| 大型业务方案 | 直播回放流水线 服务化，Redis Cluster，多 worker，多节点 WebSocket/媒体/存储 | 高并发平台 | 可横向扩展 | 架构复杂 | 高 | 高 | 只做设计理解 |
| 云服务方案 | 云对象存储、云 CDN、云直播、云监控或云 IM 等托管能力 | 快速上线或团队较小 | 稳定省运维 | 费用和厂商绑定 | 中到高 | 低到中 | 生产可选 |
| 自建方案 | 自建媒体服务器、对象存储、监控、队列和边缘节点 | 有基础设施团队 | 可控性强 | 建设和维护成本高 | 高 | 高 | 当前不建议实现 |

### 5.2 生产环境容量估算

需要提前估算：

- 同时开播房间数、平均直播时长、推流码率、每日回放存储、转码 worker 数

估算方式：

```text
先估算峰值用户行为，再换算为数据库写入、Redis key、队列任务、文件容量或广播扇出。
例如一个高峰动作每秒 1000 次，如果每次都同步写 MySQL 热点行，很快会遇到锁竞争；
学习版可以直接写库，项目展示版应增加 Redis 计数、队列聚合或缓存快照。
```

### 5.3 关键设计问题

- Laravel 负责业务控制、权限、状态和元数据，不直接承担大流量或长耗时处理。
- 中间件负责它擅长的事情：Redis 做状态和削峰，Queue 做异步任务，媒体服务器做直播流，对象存储/CDN 做文件分发。
- 所有状态变化要可追踪，失败要能重试或补偿。
- 对用户可见的数据允许最终一致时，要明确同步周期和兜底校准方式。

### 5.4 典型容量瓶颈和解决方式

| 瓶颈 | 表现 | 原因 | 解决方式 |
| --- | --- | --- | --- |
| 录制文件巨大 | 请求变慢、数据不准或任务积压 | 设计不当或容量增长过快 | 拆分异步任务、增加缓存/索引、扩展 worker 或改用专门中间件 |
| 回放转码队列积压 | 请求变慢、数据不准或任务积压 | 设计不当或容量增长过快 | 拆分异步任务、增加缓存/索引、扩展 worker 或改用专门中间件 |
| 本地磁盘容量不足 | 请求变慢、数据不准或任务积压 | 设计不当或容量增长过快 | 拆分异步任务、增加缓存/索引、扩展 worker 或改用专门中间件 |
| 直播结束后集中转码 | 请求变慢、数据不准或任务积压 | 设计不当或容量增长过快 | 拆分异步任务、增加缓存/索引、扩展 worker 或改用专门中间件 |

### 5.5 学习版到生产版的演进路线

- 本地学习版：Laravel + MySQL + Redis + 本地 storage，先跑通闭环。
- 项目展示版：引入 Redis queue、状态日志、后台管理、基础监控。
- 小型生产版：Nginx、Supervisor、对象存储、CDN、HTTPS、告警。
- 中大型生产版：多节点、独立 worker、Redis Cluster、读写分离、专门媒体/搜索/监控组件。
- 云服务方案：优先使用云点播、云直播、云 CDN、云对象存储降低运维复杂度。

### 5.6 生产环境面试讲解

如果这个模块从 Demo 变成生产系统，我会先拆清 Laravel 和中间件边界；同步请求只做必要校验和状态写入，耗时任务交给队列，高频状态交给 Redis，大文件和媒体流交给对象存储、CDN 或媒体服务器。容量估算重点看 同时开播房间数、平均直播时长、推流码率、每日回放存储、转码 worker 数。流量上来后，优先处理 录制文件巨大、回放转码队列积压。

## 7. 核心流程

### 正常流程

1. 用户在页面发起操作。
2. 浏览器请求 Laravel 接口，并携带登录态或必要参数。
3. Laravel 通过 Policy / FormRequest / Service 校验权限和输入。
4. MySQL 写入业务记录、状态或审计日志。
5. Redis 处理限流、缓存、计数、锁或在线状态。
6. Queue 处理耗时任务、通知、聚合、清理或重试。
7. 相关中间件完成媒体、存储、实时通信或监控职责。
8. 页面展示最新状态，必要时通过轮询或 WebSocket 接收结果。

### 异常流程

- 权限不足：返回 403，并记录必要审计。
- Redis 不可用：降级到数据库快照或直接提示稍后重试。
- 队列未启动：业务状态停留在 pending/processing，后台健康检查报警。
- 并发请求：使用唯一索引、Redis lock 或状态机防重复执行。
- 中间件异常：记录错误摘要，避免把底层异常直接暴露给用户。

## 8. Laravel 实现拆分

### 8.1 数据库表

- live_recordings：id、room_id、video_id、source_path、duration、size、status
- videos：source_type=live_replay、live_room_id、processing_status、publish_status
- recording_segments：recording_id、path、start_at、end_at、status

### 8.2 Model

- LiveRoom hasMany LiveRecording
- LiveRecording belongsTo Video
- Video belongsTo LiveRoom 可选

### 8.3 Controller

- LiveReplayController：回放列表和播放
- MediaRecordingCallbackController：接收录制完成回调

Controller 只负责接收请求、调用授权、组织响应；复杂状态、文件、队列和中间件调用应放到 Service 或 Job。

### 8.4 Service / Support / Action

- LiveRecordingImportService：接入录制文件
- ReplayVideoService：创建 video 并复用处理
- RecordingCleanupService：清理失败文件

### 8.5 Job

- ImportLiveRecordingJob
- TranscodeReplayToHlsJob
- CleanupFailedRecordingJob

Job 需要设置合理的 `tries`、`timeout`、`backoff`，失败后更新业务状态并写入可排查的错误摘要。

### 8.6 Event / Listener

- LiveRecordingCompleted、ReplayVideoCreated、ReplayReady、ReplayFailed

### 8.7 WebSocket / Broadcasting

- private-live-room-owner.{roomId} 推送回放生成进度

### 8.8 Policy / Middleware

- 房主可管理自己的回放；管理员可下架违规回放；观众只看 published 回放

## 10. 数据和状态设计

核心状态：

- recording.status：recording -> completed -> importing -> processing -> ready / failed
- replay publish_status：draft -> published -> hidden

状态设计原则：

- 状态迁移必须有明确触发者：用户、管理员、队列任务、媒体服务器回调或定时任务。
- 状态变化失败时要保留错误原因，并允许重试或人工处理。
- 页面展示使用业务状态，不直接暴露内部异常栈。

## 11. Redis / Queue / WebSocket 使用方式

### 11.1 Redis

- 录制导入锁防重复创建视频
- 回放生成进度缓存
- 房间回放列表缓存

### 11.2 Queue

- 录制导入、转码、清理都异步
- 转码失败进入 failed_jobs 并允许重试
- 大文件任务使用独立 transcode 队列

### 11.3 WebSocket / Reverb

- 主播后台显示回放生成中/完成/失败

## 12. 安全风险

- 录制文件丢失：完成后再创建 ready 状态
- 磁盘爆满：录制保留周期和容量监控
- 重复导入：source_path 唯一约束
- 违规直播回放：接入审核流程

## 13. 性能和扩展

- 学习版：单机 Laravel + MySQL + Redis 可以支撑低并发演示和手动验收。
- 第一类瓶颈：录制文件巨大。
- 第二类瓶颈：回放转码队列积压。
- 扩展方式：先拆异步任务和缓存，再拆专门中间件，最后考虑多节点和云服务。
- 存储扩展：本地 storage -> MinIO/S3 -> CDN。
- 队列扩展：database queue -> Redis queue -> Horizon -> 多 worker / 多机器。
- 实时扩展：单 Reverb -> 多节点 Reverb + Redis pub/sub 或专门网关。

## 14. 监控和排查

重点指标：

- 录制成功率
- 录制文件大小
- 回放转码耗时
- 回放失败率
- 存储增长量

本地排查方式：

- `storage/logs/laravel.log`
- `php artisan queue:failed`
- `docker compose logs`
- 浏览器 Network / Console
- Redis CLI 查看关键 key
- MySQL 查询状态表和日志表

## 15. 分阶段实施路线

- Phase 1：文档和录制配置验证，手动导入录制文件
- Phase 2：录制完成自动入库、转 HLS、回放列表
- Phase 3：云录制、分段回放、剪辑和生命周期管理

验收标准：

- Phase 1：本地能跑通主流程，有最小权限校验和失败提示。
- Phase 2：状态、队列、Redis、日志和后台入口完整，能作为简历项目讲解。
- Phase 3：能说明生产环境如何扩容、如何监控、如何控制成本和风险。

## 16. 面试讲解角度

### 16.1 这个功能为什么要这样设计？

因为 直播结束内容就丢失，无法形成内容沉淀和创作者资产。，所以需要把业务状态、技术组件和异常处理拆清楚。

### 16.2 Laravel 在里面负责什么？

Laravel 负责认证授权、业务状态、数据库元数据、队列派发、事件通知和后台管理。

### 16.3 中间件负责什么？

中间件负责缓存、限流、异步执行、媒体处理、实时通信、文件分发或监控采集，避免 Laravel 承担不适合的工作。

### 16.4 为什么不能全部用 Laravel 直接做？

Laravel 适合业务控制，不适合长时间转码、大文件分发、高频实时连接或大规模计数。全部塞进 Laravel 会导致请求超时、内存压力、连接数瓶颈和维护困难。

### 16.5 如果数据量 / 流量变大，怎么扩展？

先做 Redis 缓存和计数削峰，再把耗时逻辑放进队列；文件和媒体流迁移到对象存储、CDN 或媒体服务器；最后按业务压力拆分 worker、WebSocket、搜索或监控组件。

### 16.6 失败场景怎么处理？

失败要记录状态、错误摘要和可重试入口。队列任务失败进入 failed_jobs，用户看到可理解的状态，管理员能在后台查看和处理。

### 16.7 安全风险怎么处理？

围绕越权、刷接口、路径安全、敏感信息泄露和管理员误操作做防护，关键动作都要走 Policy、RateLimiter、审计日志和输入校验。

### 16.8 这个方案还有哪些不足？

学习版强调可理解和可验收，不覆盖复杂推荐、版权识别、支付结算、跨地域高可用和大型风控系统。生产环境需要按业务规模逐步引入专门服务。

## 17. 总结

直播回放的设计重点是把媒体服务器生成的录制文件安全接入 Laravel，再复用点播转码和发布体系，避免另起一套割裂流程。

## 一句话总结

直播录制与回放的核心设计是：Laravel 管业务和状态，中间件管性能和基础设施，所有高频、耗时、可失败的部分都要异步化、可观测、可重试。
