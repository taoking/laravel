# 【播放器增强、播放进度、字幕与错误上报】技术方案设计

> 来源：根据 `docs/live-video-chat/10-mainstream-roadmap.md`、`docs/live-video-chat/laravel-live-video-chat-roadmap.md` 和 `docs/live-video-chat/prompt.md` 整理。

## 1. 模块定位

播放器增强、播放进度、字幕与错误上报属于 **业务 + 技术混合模块**。

播放器体验涉及前端 hls.js 事件、进度节流、字幕文件、错误上报和后端统计。

它涉及的核心组件是：hls.js、video_watch_progress、video_subtitles、playback_error_events、Redis 节流、Queue 聚合。

## 2. 解决的问题

- 用户层面：用户可以选择清晰度、倍速播放、断点续播、打开字幕，并在播放失败时看到明确提示。
- 系统层面：后端能知道播放失败、卡顿和进度数据，用于排查和体验优化。
- 不做的问题：用户只能播放，无法恢复进度；播放失败也无法判断是权限、HLS、CDN 还是浏览器问题。
- 所在位置：它把已有 HLS 能力升级为主流视频网站的播放体验。

## 4. 推荐学习方案

当前学习项目推荐方案：

```text
方案名称：hls.js + 进度节流 + WebVTT 字幕 + 错误事件入库
核心组件：hls.js、MySQL、Redis、Queue
Laravel 职责：提供播放元数据、保存进度、管理字幕、接收错误上报
中间件职责：Redis 节流进度写入，队列聚合播放错误
数据流：播放器加载 -> 获取 HLS -> 监听 timeupdate/error -> 节流上报 -> 后端保存/聚合
适合原因：不改变媒体链路即可明显提升项目完整度
不足：真实 QoE 还需要更多前端指标和采样
后续升级：首帧耗时、卡顿率、CDN 节点错误、客户端版本维度
```

## 5. 生产环境方案、容量和架构设计

### 5.1 生产环境常见方案

| 方案 | 典型架构 | 适合规模 | 优点 | 缺点 | 成本 | 维护难度 | 是否推荐 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 小型业务方案 | Laravel + MySQL + Redis，播放体验服务 单机运行 | 学习项目到小型站点 | 实现成本低，便于排查 | 容量和高可用有限 | 低 | 低 | 学习期推荐 |
| 中型业务方案 | hls.js、video_watch_progress、video_subtitles、playback_error_events、Redis 节流、Queue 聚合，队列和缓存拆分，关键任务异步 | 有稳定用户和内容增长 | 吞吐更好，边界清晰 | 需要监控和运维 | 中 | 中 | 推荐演进 |
| 大型业务方案 | 播放体验服务 服务化，Redis Cluster，多 worker，多节点 WebSocket/媒体/存储 | 高并发平台 | 可横向扩展 | 架构复杂 | 高 | 高 | 只做设计理解 |
| 云服务方案 | 云对象存储、云 CDN、云直播、云监控或云 IM 等托管能力 | 快速上线或团队较小 | 稳定省运维 | 费用和厂商绑定 | 中到高 | 低到中 | 生产可选 |
| 自建方案 | 自建媒体服务器、对象存储、监控、队列和边缘节点 | 有基础设施团队 | 可控性强 | 建设和维护成本高 | 高 | 高 | 当前不建议实现 |

### 5.2 生产环境容量估算

需要提前估算：

- 日播放次数、timeupdate 上报间隔、字幕文件大小、错误事件采样率、播放元数据 QPS

估算方式：

```text
先估算峰值用户行为，再换算为数据库写入、Redis key、队列任务、文件容量或广播扇出。
例如一个高峰动作每秒 1000 次，如果每次都同步写 MySQL 热点行，很快会遇到锁竞争；
学习版可以直接写库，项目展示版应增加 Redis 计数、队列聚合或缓存快照。
```

### 5.3 关键设计问题

- Laravel 负责业务控制、权限、状态和元数据，不直接承担大流量或长耗时处理。
- 中间件负责它擅长的事情：Redis 做状态和削峰，Queue 做异步任务，媒体服务器做直播流，对象存储/CDN 做文件分发。
- 所有状态变化要可追踪，失败要能重试或补偿。
- 对用户可见的数据允许最终一致时，要明确同步周期和兜底校准方式。

### 5.4 典型容量瓶颈和解决方式

| 瓶颈 | 表现 | 原因 | 解决方式 |
| --- | --- | --- | --- |
| 进度每秒写库导致 MySQL 压力 | 请求变慢、数据不准或任务积压 | 设计不当或容量增长过快 | 拆分异步任务、增加缓存/索引、扩展 worker 或改用专门中间件 |
| 错误事件全量入库过大 | 请求变慢、数据不准或任务积压 | 设计不当或容量增长过快 | 拆分异步任务、增加缓存/索引、扩展 worker 或改用专门中间件 |
| 字幕文件未走 CDN 导致加载慢 | 请求变慢、数据不准或任务积压 | 设计不当或容量增长过快 | 拆分异步任务、增加缓存/索引、扩展 worker 或改用专门中间件 |

### 5.5 学习版到生产版的演进路线

- 本地学习版：Laravel + MySQL + Redis + 本地 storage，先跑通闭环。
- 项目展示版：引入 Redis queue、状态日志、后台管理、基础监控。
- 小型生产版：Nginx、Supervisor、对象存储、CDN、HTTPS、告警。
- 中大型生产版：多节点、独立 worker、Redis Cluster、读写分离、专门媒体/搜索/监控组件。
- 云服务方案：优先使用云点播、云直播、云 CDN、云对象存储降低运维复杂度。

### 5.6 生产环境面试讲解

如果这个模块从 Demo 变成生产系统，我会先拆清 Laravel 和中间件边界；同步请求只做必要校验和状态写入，耗时任务交给队列，高频状态交给 Redis，大文件和媒体流交给对象存储、CDN 或媒体服务器。容量估算重点看 日播放次数、timeupdate 上报间隔、字幕文件大小、错误事件采样率、播放元数据 QPS。流量上来后，优先处理 进度每秒写库导致 MySQL 压力、错误事件全量入库过大。

## 7. 核心流程

### 正常流程

1. 用户在页面发起操作。
2. 浏览器请求 Laravel 接口，并携带登录态或必要参数。
3. Laravel 通过 Policy / FormRequest / Service 校验权限和输入。
4. MySQL 写入业务记录、状态或审计日志。
5. Redis 处理限流、缓存、计数、锁或在线状态。
6. Queue 处理耗时任务、通知、聚合、清理或重试。
7. 相关中间件完成媒体、存储、实时通信或监控职责。
8. 页面展示最新状态，必要时通过轮询或 WebSocket 接收结果。

### 异常流程

- 权限不足：返回 403，并记录必要审计。
- Redis 不可用：降级到数据库快照或直接提示稍后重试。
- 队列未启动：业务状态停留在 pending/processing，后台健康检查报警。
- 并发请求：使用唯一索引、Redis lock 或状态机防重复执行。
- 中间件异常：记录错误摘要，避免把底层异常直接暴露给用户。

## 8. Laravel 实现拆分

### 8.1 数据库表

- video_watch_progress：user_id、video_id、position_seconds、duration_seconds、updated_at
- video_subtitles：video_id、language、label、path、is_default
- playback_error_events：video_id、user_id、code、message、current_time、user_agent、created_at

### 8.2 Model

- Video hasMany Subtitle / WatchProgress / PlaybackErrorEvent
- WatchProgress belongsTo User and Video

### 8.3 Controller

- PlaybackController：输出播放页和元数据
- WatchProgressController：save/show
- SubtitleController：upload/delete
- PlaybackErrorController：store

Controller 只负责接收请求、调用授权、组织响应；复杂状态、文件、队列和中间件调用应放到 Service 或 Job。

### 8.4 Service / Support / Action

- PlaybackMetadataService：组装 HLS、字幕、进度
- WatchProgressService：节流和合并进度
- PlaybackErrorClassifier：分类错误

### 8.5 Job

- AggregatePlaybackErrorsJob
- CleanupOldProgressJob

Job 需要设置合理的 `tries`、`timeout`、`backoff`，失败后更新业务状态并写入可排查的错误摘要。

### 8.6 Event / Listener

- PlaybackErrorReported、SubtitleUploaded、WatchProgressUpdated

### 8.7 WebSocket / Broadcasting

- 通常不需要 WebSocket；创作者后台可订阅播放错误摘要

### 8.8 Policy / Middleware

- 用户有播放权限才可读取进度；作者或管理员可上传字幕

## 10. 数据和状态设计

核心状态：

- subtitle.status：uploaded -> active / disabled
- playback_error.status：new -> aggregated -> ignored

状态设计原则：

- 状态迁移必须有明确触发者：用户、管理员、队列任务、媒体服务器回调或定时任务。
- 状态变化失败时要保留错误原因，并允许重试或人工处理。
- 页面展示使用业务状态，不直接暴露内部异常栈。

## 11. Redis / Queue / WebSocket 使用方式

### 11.1 Redis

- progress:user:{id}:video:{id} 节流 10 到 30 秒落库
- 错误事件按视频短期计数用于报警
- 热门视频播放元数据缓存

### 11.2 Queue

- 错误事件聚合异步处理
- 字幕转码/格式校验可异步
- 进度保存不走重队列，避免延迟影响体验

### 11.3 WebSocket / Reverb

- 当前不强依赖；生产可用实时指标面板推送错误峰值

## 12. 安全风险

- 进度高频写库：前端和后端双重节流
- 字幕 XSS：WebVTT 内容校验和转义
- 越权读取私有视频进度：播放接口统一鉴权
- 错误上报刷接口：限流和采样

## 13. 性能和扩展

- 学习版：单机 Laravel + MySQL + Redis 可以支撑低并发演示和手动验收。
- 第一类瓶颈：进度每秒写库导致 MySQL 压力。
- 第二类瓶颈：错误事件全量入库过大。
- 扩展方式：先拆异步任务和缓存，再拆专门中间件，最后考虑多节点和云服务。
- 存储扩展：本地 storage -> MinIO/S3 -> CDN。
- 队列扩展：database queue -> Redis queue -> Horizon -> 多 worker / 多机器。
- 实时扩展：单 Reverb -> 多节点 Reverb + Redis pub/sub 或专门网关。

## 14. 监控和排查

重点指标：

- 播放错误率
- 首帧耗时
- 断点续播使用率
- 字幕上传失败率
- 进度写入 QPS

本地排查方式：

- `storage/logs/laravel.log`
- `php artisan queue:failed`
- `docker compose logs`
- 浏览器 Network / Console
- Redis CLI 查看关键 key
- MySQL 查询状态表和日志表

## 15. 分阶段实施路线

- Phase 1：清晰度菜单、倍速、基础错误提示
- Phase 2：断点续播、WebVTT 字幕、错误上报
- Phase 3：QoE 指标、采样策略、CDN 错误分析

验收标准：

- Phase 1：本地能跑通主流程，有最小权限校验和失败提示。
- Phase 2：状态、队列、Redis、日志和后台入口完整，能作为简历项目讲解。
- Phase 3：能说明生产环境如何扩容、如何监控、如何控制成本和风险。

## 16. 面试讲解角度

### 16.1 这个功能为什么要这样设计？

因为 用户只能播放，无法恢复进度；播放失败也无法判断是权限、HLS、CDN 还是浏览器问题。，所以需要把业务状态、技术组件和异常处理拆清楚。

### 16.2 Laravel 在里面负责什么？

Laravel 负责认证授权、业务状态、数据库元数据、队列派发、事件通知和后台管理。

### 16.3 中间件负责什么？

中间件负责缓存、限流、异步执行、媒体处理、实时通信、文件分发或监控采集，避免 Laravel 承担不适合的工作。

### 16.4 为什么不能全部用 Laravel 直接做？

Laravel 适合业务控制，不适合长时间转码、大文件分发、高频实时连接或大规模计数。全部塞进 Laravel 会导致请求超时、内存压力、连接数瓶颈和维护困难。

### 16.5 如果数据量 / 流量变大，怎么扩展？

先做 Redis 缓存和计数削峰，再把耗时逻辑放进队列；文件和媒体流迁移到对象存储、CDN 或媒体服务器；最后按业务压力拆分 worker、WebSocket、搜索或监控组件。

### 16.6 失败场景怎么处理？

失败要记录状态、错误摘要和可重试入口。队列任务失败进入 failed_jobs，用户看到可理解的状态，管理员能在后台查看和处理。

### 16.7 安全风险怎么处理？

围绕越权、刷接口、路径安全、敏感信息泄露和管理员误操作做防护，关键动作都要走 Policy、RateLimiter、审计日志和输入校验。

### 16.8 这个方案还有哪些不足？

学习版强调可理解和可验收，不覆盖复杂推荐、版权识别、支付结算、跨地域高可用和大型风控系统。生产环境需要按业务规模逐步引入专门服务。

## 17. 总结

播放器增强不是只加按钮，而是把播放行为、字幕和失败信息纳入后端可观测链路，让体验和排障都有数据支撑。

## 一句话总结

播放器增强、播放进度、字幕与错误上报的核心设计是：Laravel 管业务和状态，中间件管性能和基础设施，所有高频、耗时、可失败的部分都要异步化、可观测、可重试。
