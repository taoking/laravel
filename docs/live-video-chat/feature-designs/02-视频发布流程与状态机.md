# 【视频发布流程与状态机】技术方案设计

> 来源：根据 `docs/live-video-chat/10-mainstream-roadmap.md`、`docs/live-video-chat/laravel-live-video-chat-roadmap.md` 和 `docs/live-video-chat/prompt.md` 整理。

## 1. 模块定位

视频发布流程与状态机属于 **业务 + 技术混合模块**。

视频发布同时包含内容状态、转码状态、审核状态和用户可见性，需要状态机、事务、队列事件和后台审核协同。

它涉及的核心组件是：MySQL 状态字段、FormRequest、Queue、Event、Policy、搜索索引同步。

## 2. 解决的问题

- 用户层面：创作者上传后可以编辑标题、简介、分类、标签，并在处理完成后决定发布或保持草稿。
- 系统层面：把处理状态和发布状态拆开，避免一个 status 字段同时表达转码、审核、上下架。
- 不做的问题：状态混乱会导致未转码视频被公开、审核失败内容可访问、失败任务无法重试。
- 所在位置：它连接上传、转码、审核、播放页、搜索索引和创作者后台。

## 3. 常见方案对比

| 方案 | 核心思路 | 需要组件 | 优点 | 缺点 | 适合阶段 | 是否推荐 |
| --- | --- | --- | --- | --- | --- | --- |
| 单 status 字段 | 用一个 videos.status 表示所有状态 | MySQL | 实现简单 | 语义混乱，后期难维护 | Demo | 不推荐长期使用 |
| 处理状态 + 发布状态 | processing_status 和 publish_status 分离 | MySQL、Policy | 边界清楚 | 需要更多状态流转代码 | 学习项目 | 推荐 |
| 显式状态机服务 | VideoStateService 统一处理状态迁移 | Service、Event、事务 | 可测试、可审计 | 初期代码稍多 | 项目展示版 | 推荐升级 |
| 工作流引擎 | 把审核、发布、下架作为工作流 | Workflow engine | 适合复杂组织审批 | 过度复杂 | 大型平台 | 当前不推荐 |

## 4. 推荐学习方案

当前学习项目推荐方案：

```text
方案名称：processing_status + publish_status + review_status 三状态拆分
核心组件：videos 表、video_state_logs、Queue、Event
Laravel 职责：状态校验、发布权限、事务、搜索索引同步事件
中间件职责：Redis Queue 处理转码完成后的状态推进
数据流：上传完成 -> processing -> ready -> draft -> pending_review -> published / rejected
适合原因：能解释真实平台为什么拆分技术处理状态和业务可见状态
不足：需要统一入口，避免 Controller 直接改状态
后续升级：引入 VideoStateService 和状态迁移日志
```

## 5. 生产环境方案、容量和架构设计

### 5.1 生产环境常见方案

| 方案 | 典型架构 | 适合规模 | 优点 | 缺点 | 成本 | 维护难度 | 是否推荐 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 小型业务方案 | Laravel + MySQL + Redis，视频状态机 单机运行 | 学习项目到小型站点 | 实现成本低，便于排查 | 容量和高可用有限 | 低 | 低 | 学习期推荐 |
| 中型业务方案 | MySQL 状态字段、FormRequest、Queue、Event、Policy、搜索索引同步，队列和缓存拆分，关键任务异步 | 有稳定用户和内容增长 | 吞吐更好，边界清晰 | 需要监控和运维 | 中 | 中 | 推荐演进 |
| 大型业务方案 | 视频状态机 服务化，Redis Cluster，多 worker，多节点 WebSocket/媒体/存储 | 高并发平台 | 可横向扩展 | 架构复杂 | 高 | 高 | 只做设计理解 |
| 云服务方案 | 云对象存储、云 CDN、云直播、云监控或云 IM 等托管能力 | 快速上线或团队较小 | 稳定省运维 | 费用和厂商绑定 | 中到高 | 低到中 | 生产可选 |
| 自建方案 | 自建媒体服务器、对象存储、监控、队列和边缘节点 | 有基础设施团队 | 可控性强 | 建设和维护成本高 | 高 | 高 | 当前不建议实现 |

### 5.2 生产环境容量估算

需要提前估算：

- 每日上传量、每日发布量、审核队列积压、状态日志增长量、索引同步 QPS

估算方式：

```text
先估算峰值用户行为，再换算为数据库写入、Redis key、队列任务、文件容量或广播扇出。
例如一个高峰动作每秒 1000 次，如果每次都同步写 MySQL 热点行，很快会遇到锁竞争；
学习版可以直接写库，项目展示版应增加 Redis 计数、队列聚合或缓存快照。
```

### 5.3 关键设计问题

- Laravel 负责业务控制、权限、状态和元数据，不直接承担大流量或长耗时处理。
- 中间件负责它擅长的事情：Redis 做状态和削峰，Queue 做异步任务，媒体服务器做直播流，对象存储/CDN 做文件分发。
- 所有状态变化要可追踪，失败要能重试或补偿。
- 对用户可见的数据允许最终一致时，要明确同步周期和兜底校准方式。

### 5.4 典型容量瓶颈和解决方式

| 瓶颈 | 表现 | 原因 | 解决方式 |
| --- | --- | --- | --- |
| 审核积压导致发布延迟 | 请求变慢、数据不准或任务积压 | 设计不当或容量增长过快 | 拆分异步任务、增加缓存/索引、扩展 worker 或改用专门中间件 |
| 状态字段缺索引导致列表慢 | 请求变慢、数据不准或任务积压 | 设计不当或容量增长过快 | 拆分异步任务、增加缓存/索引、扩展 worker 或改用专门中间件 |
| 发布瞬间同步索引阻塞请求 | 请求变慢、数据不准或任务积压 | 设计不当或容量增长过快 | 拆分异步任务、增加缓存/索引、扩展 worker 或改用专门中间件 |

### 5.5 学习版到生产版的演进路线

- 本地学习版：Laravel + MySQL + Redis + 本地 storage，先跑通闭环。
- 项目展示版：引入 Redis queue、状态日志、后台管理、基础监控。
- 小型生产版：Nginx、Supervisor、对象存储、CDN、HTTPS、告警。
- 中大型生产版：多节点、独立 worker、Redis Cluster、读写分离、专门媒体/搜索/监控组件。
- 云服务方案：优先使用云点播、云直播、云 CDN、云对象存储降低运维复杂度。

### 5.6 生产环境面试讲解

如果这个模块从 Demo 变成生产系统，我会先拆清 Laravel 和中间件边界；同步请求只做必要校验和状态写入，耗时任务交给队列，高频状态交给 Redis，大文件和媒体流交给对象存储、CDN 或媒体服务器。容量估算重点看 每日上传量、每日发布量、审核队列积压、状态日志增长量、索引同步 QPS。流量上来后，优先处理 审核积压导致发布延迟、状态字段缺索引导致列表慢。

## 7. 核心流程

### 正常流程

1. 用户在页面发起操作。
2. 浏览器请求 Laravel 接口，并携带登录态或必要参数。
3. Laravel 通过 Policy / FormRequest / Service 校验权限和输入。
4. MySQL 写入业务记录、状态或审计日志。
5. Redis 处理限流、缓存、计数、锁或在线状态。
6. Queue 处理耗时任务、通知、聚合、清理或重试。
7. 相关中间件完成媒体、存储、实时通信或监控职责。
8. 页面展示最新状态，必要时通过轮询或 WebSocket 接收结果。

### 异常流程

- 权限不足：返回 403，并记录必要审计。
- Redis 不可用：降级到数据库快照或直接提示稍后重试。
- 队列未启动：业务状态停留在 pending/processing，后台健康检查报警。
- 并发请求：使用唯一索引、Redis lock 或状态机防重复执行。
- 中间件异常：记录错误摘要，避免把底层异常直接暴露给用户。

## 8. Laravel 实现拆分

### 8.1 数据库表

- videos：id、user_id、title、description、processing_status、publish_status、review_status、published_at
- video_state_logs：video_id、from_state、to_state、actor_id、reason
- categories：id、name、slug
- tags：id、name、slug
- tag_video：video_id、tag_id

### 8.2 Model

- Video belongsTo User / Category
- Video belongsToMany Tag
- Video hasMany VideoStateLog

### 8.3 Controller

- VideoPublishController：publish、unpublish、submitReview
- VideoMetadataController：编辑标题、简介、标签，不直接处理转码

Controller 只负责接收请求、调用授权、组织响应；复杂状态、文件、队列和中间件调用应放到 Service 或 Job。

### 8.4 Service / Support / Action

- VideoStateService：校验迁移是否合法
- VideoPublishService：发布前检查转码、审核、权限
- SearchIndexSyncService：发布后同步索引

### 8.5 Job

- SyncVideoSearchIndexJob
- NotifySubscribersVideoPublishedJob
- CleanupRejectedDraftJob

Job 需要设置合理的 `tries`、`timeout`、`backoff`，失败后更新业务状态并写入可排查的错误摘要。

### 8.6 Event / Listener

- VideoReady、VideoSubmittedForReview、VideoPublished、VideoRejected、VideoHidden

### 8.7 WebSocket / Broadcasting

- private-user.{id} 推送处理完成
- private-admin.moderation 推送待审核任务

### 8.8 Policy / Middleware

- 作者可编辑草稿，管理员可下架，审核员可通过或拒绝

## 10. 数据和状态设计

核心状态：

- processing_status：pending -> processing -> ready / failed
- publish_status：draft -> pending_review -> published -> hidden / blocked
- review_status：none -> pending -> approved / rejected

状态设计原则：

- 状态迁移必须有明确触发者：用户、管理员、队列任务、媒体服务器回调或定时任务。
- 状态变化失败时要保留错误原因，并允许重试或人工处理。
- 页面展示使用业务状态，不直接暴露内部异常栈。

## 11. Redis / Queue / WebSocket 使用方式

### 11.1 Redis

- 发布按钮防重复使用短 TTL lock
- 热门列表缓存只读取 published 视频
- 草稿列表可以不缓存

### 11.2 Queue

- 转码完成、索引同步、通知粉丝都应异步
- 发布状态更新本身同步事务完成

### 11.3 WebSocket / Reverb

- 创作者后台可通过 private channel 接收 ready / failed / approved 事件

## 12. 安全风险

- 未处理完成就发布：发布前检查 processing_status=ready
- 重复提交审核：状态迁移加锁或唯一约束
- 审核绕过：publish 动作必须经过 Policy
- 搜索索引脏数据：监听状态变化删除 hidden/blocked 文档

## 13. 性能和扩展

- 学习版：单机 Laravel + MySQL + Redis 可以支撑低并发演示和手动验收。
- 第一类瓶颈：审核积压导致发布延迟。
- 第二类瓶颈：状态字段缺索引导致列表慢。
- 扩展方式：先拆异步任务和缓存，再拆专门中间件，最后考虑多节点和云服务。
- 存储扩展：本地 storage -> MinIO/S3 -> CDN。
- 队列扩展：database queue -> Redis queue -> Horizon -> 多 worker / 多机器。
- 实时扩展：单 Reverb -> 多节点 Reverb + Redis pub/sub 或专门网关。

## 14. 监控和排查

重点指标：

- 待审核视频数
- 发布成功率
- 状态迁移失败数
- 草稿转发布耗时
- 索引同步失败数

本地排查方式：

- `storage/logs/laravel.log`
- `php artisan queue:failed`
- `docker compose logs`
- 浏览器 Network / Console
- Redis CLI 查看关键 key
- MySQL 查询状态表和日志表

## 15. 分阶段实施路线

- Phase 1：拆 processing_status 和 publish_status，发布前校验 ready
- Phase 2：增加 review_status、state logs、发布事件
- Phase 3：搜索索引同步、审核工作台、状态迁移审计

验收标准：

- Phase 1：本地能跑通主流程，有最小权限校验和失败提示。
- Phase 2：状态、队列、Redis、日志和后台入口完整，能作为简历项目讲解。
- Phase 3：能说明生产环境如何扩容、如何监控、如何控制成本和风险。

## 16. 面试讲解角度

### 16.1 这个功能为什么要这样设计？

因为 状态混乱会导致未转码视频被公开、审核失败内容可访问、失败任务无法重试。，所以需要把业务状态、技术组件和异常处理拆清楚。

### 16.2 Laravel 在里面负责什么？

Laravel 负责认证授权、业务状态、数据库元数据、队列派发、事件通知和后台管理。

### 16.3 中间件负责什么？

中间件负责缓存、限流、异步执行、媒体处理、实时通信、文件分发或监控采集，避免 Laravel 承担不适合的工作。

### 16.4 为什么不能全部用 Laravel 直接做？

Laravel 适合业务控制，不适合长时间转码、大文件分发、高频实时连接或大规模计数。全部塞进 Laravel 会导致请求超时、内存压力、连接数瓶颈和维护困难。

### 16.5 如果数据量 / 流量变大，怎么扩展？

先做 Redis 缓存和计数削峰，再把耗时逻辑放进队列；文件和媒体流迁移到对象存储、CDN 或媒体服务器；最后按业务压力拆分 worker、WebSocket、搜索或监控组件。

### 16.6 失败场景怎么处理？

失败要记录状态、错误摘要和可重试入口。队列任务失败进入 failed_jobs，用户看到可理解的状态，管理员能在后台查看和处理。

### 16.7 安全风险怎么处理？

围绕越权、刷接口、路径安全、敏感信息泄露和管理员误操作做防护，关键动作都要走 Policy、RateLimiter、审计日志和输入校验。

### 16.8 这个方案还有哪些不足？

学习版强调可理解和可验收，不覆盖复杂推荐、版权识别、支付结算、跨地域高可用和大型风控系统。生产环境需要按业务规模逐步引入专门服务。

## 17. 总结

视频状态机的重点不是字段多，而是把技术处理、业务发布、审核可见性拆开，让每次状态变化都有合法入口和可追踪记录。

## 一句话总结

视频发布流程与状态机的核心设计是：Laravel 管业务和状态，中间件管性能和基础设施，所有高频、耗时、可失败的部分都要异步化、可观测、可重试。
